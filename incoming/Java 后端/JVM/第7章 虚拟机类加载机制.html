第7章 虚拟机类加载机制
  • 7.1 概述
    • 类加载机制：Java虚拟机把描述类的数据从Class文件加载到内存，并对数据进行校验、转换解析和初始化，最终形成可以被虚拟机直接使用的Java类型
    • 在Java语言里面，类型的加载、连接和初始化过程都是在程序运行期间完成的，虽然增加一些开销但提供了极高的扩展性和灵活性
  • 7.2 类加载的时机
    • 整个生命周期将会经历加载、验证、准备、解析、初始化、使用和卸载七个阶段，其中验证、准备、解析三个部分统称为连接
    • 加载、验证、准备、初始化和卸载这五个阶段的顺序是确定的，解析阶段不一定，因为它要支持Java的动态绑定或晚期绑定
      这里写的是按部就班地“开始”，而不是按部就班地“进行”或按部就班地“完成”，强调这点是因为这些阶段通常都是互相交叉地混合进行的，会在一个阶段执行的过程中调用、激活另一个阶段。
    • 没有规定什么时候加载，但规定了有且只有六种情况必须立即对类进行初始化（主动引用）
      • （1）遇到new、getstatic、putstatic或invokestatic这四条字节码指令时，如果类型没有进行过初始化，则需要先触发其初始化阶段。能够生成这四条指令的典型Java代码场景有：
        • 使用new关键字实例化对象的时候
        • 读取或设置一个类型的静态字段的时候（被final修饰、已在编译期把结果放入常量池的静态字段除外）
        • 调用一个类型的静态方法的时候
      • （2）使用java.lang.reflect包的方法对类型进行反射调用的时候，如果类型没有进行过初始化，则需要先触发其初始化。
      • （3）当初始化类的时候，如果发现其父类还没有进行过初始化，则需要先触发其父类的初始化。
      • （4）当虚拟机启动时，用户需要指定一个要执行的主类（包含main()方法的那个类），虚拟机会先初始化这个主类。
      • （5）当使用JDK 7新加入的动态语言支持时，如果一个java.lang.invoke.MethodHandle实例最后的解析结果为REF_getStatic、REF_putStatic、REF_invokeStatic、REF_newInvokeSpecial四种类型的方法句柄，并且这个方法句柄对应的类没有进行过初始化，则需要先触发其初始化。
      • （6）当一个接口中定义了JDK 8新加入的默认方法（被default关键字修饰的接口方法）时，如果有这个接口的实现类发生了初始化，那该接口要在其之前被初始化。
    • 被动引用不会触发初始化
      • （1）对于静态字段， 只有直接定义这个字段的类才会被初始化。因此通过其子类来引用父类中定义的静态字段，只会触发父类的初始化而不会触发子类的初始化。至于是否要触发子类的加载和验证阶段，在《Java虚拟机规范》中并未明确规定，所以这点取决于虚拟机的具体实现
        只会输出“SuperClass init！”，而不会输出“SubClass init！”
      • （2）通过数组定义来引用类，不会触发此类的初始化
        数组里放的是对象
      • （3）常量在编译阶段会存入调用类的常量池中，本质上没有直接引用到定义常量的类，因此不会触发定义常量的类的初始化
        final修饰
    • 接口也有初始化过程，但是一个接口在初始化时，并不要求其父接口全部都完成了初始化，只有在真正使用到父接口的时候（如引用接口中定义的常量）才会初始化。而一个类初始化时，要求其父类全部都初始化过。
  • 7.3 类加载的过程
    • 7.3.1 加载
      • “加载”是“类加载”的一个过程，不要混淆
      • 要做三件事：
        • 1. 通过一个类的全限定名获取定义此类的二进制字节流
          可以从压缩包、网络、运行中（动态代理）等获取，没有说必须从Class文件中获取
        • 2. 将这个字节流所代表的静态存储结构转化为方法区的运行时数据结构。
        • 3. 在内存中生成一个代表这个类的java.lang.Class对象，作为方法区这个类的各种数据的访问入口。
      • 非数组类的加载
        • 既可以使用Java虚拟机里内置的引导类加载器来完成，也可以由用户自定义的类加载器去完成
      • 数组类的加载（数组本身不通过类加载器创建，由Java虚拟机直接在内存中动态构造出来）
        • 组件类型(Component Type)：数组去掉一个维度后的类型。
          String[][]的组件类型是String[]。 String[]的组件类型是String。 int[]的组件类型是int。
        • 元素类型(Element Type)：数组去掉所有维度后的类型。
          String[][]的元素类型是String。 String[]的元素类型是String。 int[]的元素类型是int。
        • 如果组件是引用类型（比如类、接口）
          • 递归采用本节中定义的加载过程去加载这个组件类型，数组C将被标识在加载该组件类型的类加载器的类名称空间上。
            解释：如果想创建一个String[]数组，JVM会先去看String这个组件类型。它会问：“String是谁加载的？”假设String是由“A类加载器”加载的。那么JVM在动态创建出String[]这个类之后，就会给它盖个章，宣布String[]的“户口”也属于“A类加载器”。
          • 为什么这么做？这保证了类型的唯一性。由不同类加载器加载的同一个类是不同的类型。所以，由“A类加载器”加载的String所构成的String[]，和由“B类加载器”加载的String所构成的String[]，是完全两个不同的类型！
        • 如果组件是基本数据类型（比如int，char）
          • （例如int[]数组的组件类型为int），Java虚拟机将会把数组C标记为与引导类加载器关联。
          • 解释：如果你想创建一个int[]数组，它的组件类型是int。int是Java语言自带的基本类型，它不通过任何一个普通的类加载器加载，它天生就存在。在JVM的世界里，这种“天生存在”的东西，都归“根正苗红”的引导类加载器(Bootstrap ClassLoader)管理。所以，所有基本数据类型的数组，其“户口”都属于引导类加载器。
        • 数组类的可访问性与它的组件类型的可访问性一致，如果组件类型不是引用类型，它的数组类的可访问性将默认为public，可被所有的类和接口访问到。
      • 无论普通类还是数组类，当“加载”这个阶段完成后，Java虚拟机外部的二进制字节流就按照虚拟机所设定的格式存储在方法区之中了，会在Java堆内存中实例化一个java.lang.Class类的对象
        1. 它的类型数据被存放在了方法区，包含了它的所有信息，比如它的父类是谁、有哪些方法等。这是给JVM自己看的，是内部数据。 2. 同时，JVM会在堆内存里，创建一个与之一一对应的java.lang.Class类型的对象。这是提供给程序员使用的“接口”。我们平时写的String.class或int[].class，拿到的就是这个在堆里的Class对象。通过这个对象，我们可以使用反射等技术来访问方法区里那个类的“图纸”信息。
      • 加载阶段与连接阶段的部分动作（如一部分字节码文件格式验证动作）是交叉进行的，加载阶段尚未完成，连接阶段可能已经开始
    • 7.3.2 验证
      • 验证是连接阶段的第一步，这一阶段的目的是确保Class文件的字节流中包含的信息符合《Java虚拟机规范》的全部约束要求，保证这些信息被当作代码运行后不会危害虚拟机自身的安全
      • 1. 文件格式验证
        • 验证字节流是否符合Class文件格式的规范，并且能被当前版本的虚拟机处理
          比如：是否以魔数0xCAFEBABE开头。 指向常量的各种索引值中是否有指向不存在的常量或不符合类型的常量
        • 这阶段的验证是基于二进制字节流进行的，只有通过了这个阶段的验证之后，这段字节流才被允许进入Java虚拟机内存的方法区中进行存储，所以后面的三个验证阶段全部是基于方法区的存储结构上进行的，不会再直接读取、操作字节流了。
      • 2. 元数据验证
        • 对字节码描述的信息进行语义分析，以保证其描述的信息符合《Java语言规范》的要求
          比如：这个类是否有父类（除了java.lang.Object之外，所有的类都应当有父类）。 这个类的父类是否继承了不允许被继承的类（被final修饰的类）。
      • 3. 字节码验证
        • 是整个验证过程中最复杂的一个阶段，主要目的是通过数据流分析和控制流分析，确定程序语义是合法的、符合逻辑的
          比如：保证任何跳转指令都不会跳转到方法体以外的字节码指令上。 不会一个int类型的数据，使用时却按long类型来加载入本地变量表中的情况发生
        • 如果一个方法体通过了字节码验证，也仍然不能保证它一定就是安全的。不可能用程序来准确判定一段程序是否存在Bug
      • 4. 符号引用验证
        • 发生在虚拟机将符号引用转化为直接引用的时候，这个转化动作将在连接的第三阶段——解析阶段中发生
        • 符号引用验证可以看作是对类自身以外（常量池中的各种符号引用）的各类信息进行匹配性校验，通俗来说就是，该类是否缺少或者被禁止访问它依赖的某些外部类、方法、字段等资源。
          比如：符号引用中通过字符串描述的全限定名是否能找到对应的类 符号引用中的类、字段、方法的可访问性（private、protected、public、<package>）是否可被当前类访问
        • 重要但非必须
    • 7.3.3 准备
      • 正式为类中定义的变量（即静态变量，被static修饰的变量）分配内存并设置类变量初始值
      • 但是
        • 这时仅包括类变量，而不包括实例变量，实例变量会在对象实例化时随着对象一起分配在Java堆中
        • 初始值默认为零值
        • final修饰的设置的就是用户定义的值
    • 7.3.4 解析
      • Java虚拟机将常量池内的符号引用替换为直接引用的过程
      • 符号引用：是一个描述性的标识符，它以一组文本符号的形式，定义了在程序中被引用的一个目标。这个目标可以是类、接口、字段或方法。它存在于编译后的Class文件中的常量池（ConstantPool）里。
        构成符号引用通常由几部分文本信息构成，例如一个方法的符号引用会包含： 类的完全限定名：例如"java/lang/System" 字段或方法的名称：例如"out"或"println" 字段或方法的描述符：描述字段类型或方法的参数类型和返回类型，例如"(Ljava/lang/String;)V"
      • 直接引用：是一个指针或者内存地址，它直接指向已经存在于JVM内存中的目标。这个目标就是符号引用所描述的那个类、字段或方法。
        形式直接引用不是一个固定的格式，它的具体形式取决于JVM的实现。通常可能是： 内存指针：直接指向目标在内存中的起始地址。 相对偏移量：一个相对于某个基准地址的偏移量，通过基准地址+偏移量可以找到目标。 句柄：一个间接的引用，它指向一个句柄池，句柄中再包含指向目标的实际指针。
      • 对同一个符号引用进行多次解析请求是很常见的事情
        • 除invokedynamic指令以外，虚拟机实现可以对第一次解析的结果进行缓存，譬如在运行时直接引用常量池中的记录，并把常量标识为已解析状态，从而保持解析一致性和避免解析动作重复进行
        • 对于invokedynamic指令，必须等到程序实际运行到这条指令时，解析动作才能进行
      • 何时发生
        • 静态解析（或早期解析）：在类加载时就进行解析。
        • 动态链接（或晚期解析）：在程序第一次实际使用该符号引用时才进行解析。Java中绝大部分的解析是动态解析
      • 为何需要这个过程：这个两阶段的过程是Java语言实现平台无关性和动态链接的核心
        • 1. 平台无关性：javac编译器只负责生成包含符号引用的、平台无关的Class文件。这样，一份编译好的代码可以不经修改地在任何平台的JVM上运行。
        • 2. 动态链接：具体的内存地址分配是运行时的JVM负责的。JVM在运行时，会根据自身的内存管理方式，将加载的类、方法等安置在特定内存位置，然后才建立引用关系。这允许程序在运行时动态地加载、链接和使用不同的类。
    • 7.3.5 初始化
      • 初始化阶段就是执行类构造器 <clinit>() 方法的过程。 <clinit>() 并不是程序员在Java代码中直接编写的方法，它是Javac编译器的自动生成物
      • 生成过程：编译器会扫描类中所有的static变量赋值语句和static代码块，然后按照它们在源代码中出现的顺序，将这些代码逻辑合并成一个 <clinit>() 方法。静态语句块中只能访问到定义在静态语句块之前的变量，定义在它之后的变量，在前面的静态语句块可以赋值，但是不能访问
        • 生成条件：如果一个类中既没有静态变量的赋值操作，也没有静态代码块，那么编译器不会为这个类生成 <clinit>() 方法。
        • 接口的特殊性：接口也可以有 <clinit>() 方法，用于初始化接口中定义的静态变量。但与类不同的是，执行接口的 <clinit>() 方法不需要先执行父接口的 <clinit>() 方法， 因为只有当父接口中定义的变量被使用时，父接口才会被初始化
      • 执行时机： <clinit>() 的执行时机比较特殊，由JVM严格控制：
        • 1. 唯一性：对于同一个类加载器，一个类的 <clinit>() 方法只会被调用一次。
        • 2. 线程安全：JVM会保证 <clinit>() 方法在多线程环境下的同步。如果多个线程同时去初始化一个类，只有一个线程会执行 <clinit>() 方法，其他线程都会阻塞等待，直到该方法执行完毕。
        • 3. 父类优先：在执行子类的 <clinit>() 方法之前，JVM会保证其父类的 <clinit>() 方法已经执行完毕。这意味着最顶层的java.lang.Object类是最先被初始化的（虽然它没有 <clinit>() 内容）。
  • 7.4 类加载器
    • 类加载器实现了通过一个类的全限定名来获取描述该类的二进制字节流，以便让应用程序自己决定如何去获取所需的类
    • 7.4.1 类与类加载器
      • 对于任意一个类，都必须由加载它的类加载器和这个类本身一起共同确立其在Java虚拟机中的唯一性，每一个类加载器，都拥有一个独立的类名称空间。如果类加载器不一样，这两类必然不相等
    • 7.4.2 双亲委派模型
      • 启动类加载器是虚拟机自身的一部分，其他所有类加载器独立存在于虚拟机外部
      • 3个系统提供的类加载器：
        • 启动类加载器：负责加载存放在 <JAVA_HOME>\lib目录，或者被-Xbootclasspath参数所指定的路径中存放的
        • 扩展类加载器：负责加载<JAVA_HOME>\lib\ext目录中，或者被java.ext.dirs系统变量所指定的路径中所有的类库。
        • 应用程序类加载器：负责加载用户类路径 （ClassPath）上所有的类库。如果应用程序中没有 自定义过自己的类加载器，一般情况下这个就是程序中默认的类加载器
      • 类加载器双亲委派模型：如果一个类加载器收到了类加载的请求，它首先不会自己去尝试加载这个类，而是把这个请求委派给父类加载器去完成，每一个层次的类加载器都是如此，因此所有的加载请求最终都应该传送到最顶层的启动类加载器中，只有当父加载器反馈自己无法完成这个加载请求（它的搜索范围中没有找到所需的类）时，子加载器才会尝试自己去完成加载。假如父类加载器加载失败，抛出ClassNotFoundException异常的话，才调用自己的findClass()方法尝试进行加载。
        Application ClassLoader先接受到请求，但是不查找，直接给上级Extension ClassLoader，Extension ClassLoader接受到后也不查找，直接给上级Bootstrap ClassLoader，Bootstrap ClassLoader接受到后开始查找，如果查找到就流程结束，没查找到就返回下一级Extension ClassLoader，Extension ClassLoader接受到后开始查找，如果查找到就流程结束，没查找到就返回下一级Application ClassLoader
        • 保证了：
          • 1. 优先使用系统提供的、更上层的类加载器来加载，确保了基础类的唯一性和安全性。
          • 2. 只有当所有上级都无法加载时，才给自定义的加载器一个“兜底”的机会，从网络、特定文件系统、数据库等地方加载类，实现功能的扩展。
    • 7.4.3 破坏双亲委派模型
      • 第一次“被破坏”发生在双亲委派模型出现之前，为了避免loadClass()被子类覆盖，官方添加一个新的protected方法findClass()，并引导用户编写的类加载逻辑时尽可能去重写这个方法，而不是在loadClass()中编写代码
      • 双亲委派模型的第二次“被破坏”是由这个模型自身的缺陷导致，解决不了基础类型又要调用回用户的代码的问题：引入线程上下文类加载器，这个类加载器可以通过java.lang.Thread类的setContext-ClassLoader()方法进行设置，如果创建线程时还未设置，它将会从父线程中继承一个，如果在应用程序的全局范围内都没有设置过的话，那这个类加载器默认就是应用程序类加载器
      • 第三次“被破坏”是由于用户对程序动态性的追求而导致的
  • 7.5 Java模块化系统
    • 在JDK 9中引入的Java模块化系统（Java Platform Module System，JPMS）是对Java技术的一次重要升级
      • 可靠的依赖： 模块可以显式声明依赖。JVM在启动时就能验证依赖是否完整，避免了在运行时才抛出 ClassNotFoundException。
      • 可配置的封装隔离： 模块可以精确控制哪些 public 类型可以被哪些其他模块访问（通过 exports 关键字），解决了以前 public 类型在JAR包间“无条件”可访问的问题。
    • 7.5.1 模块的兼容性
      • JPMS引入了“模块路径”（ModulePath）来与传统的“类路径”（ClassPath）相对应。
        某个类库到底是模块还是传统的JAR包，只取决于它存放在哪种路径上。只要是放在类路径上的JAR文件，无论其中是否包 含模块化信息（是否包含了module-info.class文件），它都会被当作传统的JAR包来对待；相应地，只要放在模块路径上的JAR文件，即使没有使用JMOD后缀，甚至说其中并不包含module-info.class文件，它也仍然会被当作一个模块来对待。
      • 匿名模块 (Unnamed Module)： 放在类路径上的所有JAR包，会被视为一个大的“匿名模块”。它几乎没有隔离，可以看到所有模块导出的包。
      • 具名模块 (Named Module)： 放在模块路径上、且包含 module-info.class 的标准模块。它们受到严格的封装隔离限制。
      • 自动模块 (Automatic Module)： 放在模块路径上、但不包含 module-info.class 的传统JAR包。它会自动依赖所有其他模块，并导出自己所有的包，以此来兼容传统JAR包。
    • 7.5.2 模块化下的类加载器
      • 加载器更名： “扩展类加载器”（Extension Class Loader）被“平台类加载器”（Platform Class Loader）取代。
      • 继承关系改变： 平台类加载器和应用程序类加载器不再继承自 java.net.URLClassLoader。
      • 双亲委派模型的调整： 双亲委派模型依然存在，但发生了变动。当平台和应用程序类加载器收到加载请求时，会先判断该类是否属于某个系统模块，如果属于，则优先委派给负责该模块的加载器（而不是无条件先给父加载器）。这可能是对双亲委派的“第四次破坏”。
