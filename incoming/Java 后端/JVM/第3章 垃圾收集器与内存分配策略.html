第3章 垃圾收集器与内存分配策略
  • 3.1 概述
    • Java堆和方法区需要回收
  • 3.2 对象已死？
    • 3.2.1 引用计数算法
      • 思路：给对象一个引用计数器，有一个地方引用这个对象时，这个对象的计数器值加一；引用失效时就减一；当计数器值为零的对象就是不可能再被使用的
      • 问题：难以解决循环依赖问题。互相引用对方使计数器值不为零导致无法回收，即使这两个对象已经不能再被访问
      • 优点：简单、判断效率高
    • 3.2.2 可达性分析算法
      • 思路：使用GC Roots根据引用关系向下搜索，搜索过程走过的路径叫“引用链”，搜索得到说明可达，搜索不到或者说某个对象到GC Roots间没有引用链相连则说明不可达，可回收
      • GC Roots包含：
        • （1）在虚拟机栈（栈帧中的本地变量表）中引用的对象，譬如各个线程被调用的方法堆栈中使用到的参数、局部变量、临时变量等。方法里的局部变量。方法在执行，变量就活着。
        • （2）在方法区中类静态属性引用的对象，譬如Java类的引用类型静态变量。生命周期和类一样长。
        • （3）在方法区中常量引用的对象，譬如字符串常量池（String Table）里的引用。
          String s1 = "hello"; s1在虚拟机栈的局部变量表（slot 0），"hello"在常量池中，字符串的不可变性，实现“共享”，节省内存 String s3 = new String("hello"); s3在虚拟机栈的局部变量表（slot 1），"hello"在堆中，强制创建新对象
        • （4）Native方法引用的对象： JNI调用的C/C++代码中使用的Java对象。
        • （5）Java虚拟机内部的引用，如基本数据类型对应的Class对象，一些常驻的异常对象（比如NullPointExcepiton、OutOfMemoryError）等，还有系统类加载器。
        • （6）所有被synchronized锁持有的对象：作为“锁”的对象，必须存活以保证线程同步正常。
        • （7）反映Java虚拟机内部情况的JMXBean、JVMTI中注册的回调、本地代码缓存等。
        • （8）除了这些固定的GC Roots集合以外，根据用户所选用的垃圾收集器以及当前回收的内存区域不同，还可以有其他对象“临时性”地加入
    • 3.2.3 再谈引用
      • 强引用：如Dog d = new Dog(); 只要强引用关系在，垃圾收集器就永远不会回收被引用的对象。只要没设为 null，垃圾回收器哪怕把系统搞崩（OOM），也不敢动它。d = null了才可能会被回收
      • 软引用：还有用但非必须的对象。只有在系统要内存溢出前才会回收软引用的对象，如果这次回收还没有足够的内存才会抛出内存溢出异常
      • 弱引用：也是非必须对象，但比软引用再弱一些。无论内存是否足够，弱引用的对象只能存活到下一次垃圾回收为止，都会回收掉
      • 虚引用：无法通过虚引用来获得一个对象实例。为一个对象设置虚引用只是为了能够在这个对象被回收时收到一个系统通知
    • 3.2.4 生存还是死亡？
      • 思路：要回收一个对象得经历两个标记过程
        • 1. 可达性分析是否与GC Roots相连接，没有的话第一次标记，标记后进行筛选，筛选有没有执行过finalize()方法的或有没有重写finalize()方法的，执行过的不行， 没重写的不行
          任何一个对象的finalize()方法都只会被系统自动调用一次，如果对象面临下一次回收，它的finalize()方法不会被再次执行
        • 2. 有必要执行finalize方法的对象会被放入F-Queue的队列中，并稍后由一条由虚拟机自动创建、低调度优先级的Finalizer线程执行他们的finalize()方法，这里的执行是指虚拟机会触发这个方法开始运行，但不承诺得等到他运行结束
          怕执行缓慢或死循环导致队列其他对象一直等待，甚至内存回收子系统崩溃
        • 3. 如果finalize()方法中重新与GC Roots产生关联则移除回收，否则真的要被回收了
    • 3.2.5 回收方法区
      • 不要求虚拟机在方法区中实现垃圾收集
      • 主要回收：
        • 废弃的常量：没有任何字符串对象引用常量池中的“Java”常量
        • 不再使用的类型：需同时达到以下三条件，达到了也只是允许回收不是必须回收
          • 该类所有的实例都已经被回收，也就是Java堆中不存在该类及其任何派生子类的实例。
          • ·加载该类的类加载器已经被回收，这个条件除非是经过精心设计的可替换类加载器的场景，如OSGi、JSP的重加载等，否则通常是很难达成的。
          • 该类对应的java.lang.Class对象没有在任何地方被引用，无法在任何地方通过反射访问该类的方法。
  • 3.3 垃圾收集算法
    • 垃圾收集算法可以划分为“引用计数式垃圾收集”和“追踪式垃圾收集”两大类
    • 3.3.1 分代收集理论
      • 三种分代假说
        • 弱分代假说：绝大多数对象很快就消亡了
        • 强分代假说：熬过越多次垃圾收集过程的对象就越难以消亡
          • 根据以上两种，Java堆分为新生代和老年代
        • 跨代引用假说：跨代引用相比于同代引用占比极少
          • 如果为了少量跨代引用扫描整个老年代，花销大，所以建立记忆集
            记忆集把老年代划分出若干区域，标识出哪个区域存在跨代引用，此后发生Minor GC时，只有这些区域里的对象才会被加入GC Roots进行扫描
      • 部分收集
        • 新生代收集（Minor GC/Young GC）
        • 老年代收集（Major GC/Old GC）
        • 混合收集（Mixed GC）：目标是整个新生代和部分老年代的垃圾收集
      • 整堆收集：收集整个Java堆和方法区的垃圾收集
    • 3.3.2 标记-清除算法
      • 思想：分为“标记”和“清除”两个阶段，首先对（不）需要回收的对象进行标记，然后统一回收所有（不）被标记的对象
      • 优点：简单，后续收集算法大都以改进它作为基础
      • 缺点：（1）执行效率不稳定，两个阶段的执行效率都随对象数量增加而降低 （2）导致内存空间碎片化，容易没有连续空间放大对象不得不提前触发另一次垃圾收集
    • 3.3.3 标记-复制算法
      • 思想：把内存区域分为大小相等的两块，每次只使用其中一块。当这块的内存用完了，就把存活对象复制到另一块，再将已使用的那块一次清理掉
      • 优点：简单高效
      • 缺点：只剩一半可用内存了，太浪费
      • 现在的虚拟机大多采用复制算法回收新生代
      • Apple式回收：把新生代分为一块较大的Eden空间和两块较小的Survivor空间，每次分配内存只使用Eden和其中一块survivor区域，当发生垃圾收集时，把这两块区域存活对象一次性复制到另一块survivor区域中，然后清理掉这两块空间
        • 默认Eden和Survivor的大小比例是8∶1，也就是新生代可用内存为新生代内存空间的90%
        • 当survivor空间不够放存活对象时，需要依赖老年代进行分配担保直接进入老年代
    • 3.3.4 标记-整理算法
      • 思想：分为“标记”和“整理”阶段，标记过程和标记清除算法的一样，整理则是让所有存活的对象往内存一侧移动，然后直接清理边界外的对象
      • 优点：(1)解决内存碎片化问题；(2)移动对象能带来更高的吞吐量（因为不移动对象极大地降低了用户程序的效率）
      • 缺点：Stop The World：移动存活对象并更新引用他们的地方必须全程暂停用户应用
  • 3.4 HotSpot的算法细节实现
    • 3.4.1 根节点枚举
      • 根节点枚举必须暂停用户线程
      • 改进：使用OopMap记录当前方法的栈帧和寄存器里哪些位置的值是对象引用
        • 类加载完成后，虚拟机就知道对象里哪个地方存的是引用，这样垃圾收集器就可以根据OopMap瞬间拿到了所有在栈上的根引用，并顺着这些根引用便利堆里的对象，这样就不用从线程的栈内存的第一个字节开始逐个看是引用还是整数，耗时且可能不准
        • OopMap 是在“编译期”（JIT编译时）生成的，而不是在“运行期”（线程跑到安全点时）生成的。
        • OopMap 是针对方法中的安全点的，而不是类或对象
          我们来梳理这个从属关系： 1. 一个类里定义了很多方法。 2. 当JVM（通过JIT编译器）决定要编译一个方法时，它会生成这个方法的机器码。 3. 在生成机器码的过程中，JIT会在它认为合适的地方（比如循环末尾）插入一些安全点。 4. 对于每一个插入的安全点，JIT都会在编译时同时生成一个对应的 OopMap。 所以，OopMap 是一种元数据。它和某个具体的方法、某个具体的安全点地址绑定在一起。 它的作用是“查地图”，它回答的是这样一个问题： “当一个线程的执行暂停在 MyClass.myMethod() 这个方法的 0x1234ABCD 这个安全点地址时，请告诉我，在这个线程的栈帧和CPU寄存器里，哪些位置上存放的是对象引用（Oop）？
    • 3.4.2 安全点
      • 每条指令都生成OopMap会消耗大量存储空间，因此只在特定位置生成，这个位置就叫安全点
      • 安全点的选择不能太少让每次收集器等待时间过长，也不能太多增大运行负荷，要以“是否具有让程序长时间运行的特征”为标准，例如方法调用、循环跳转、异常跳转
      • 如何让所有线程都跑到安全点后停下来
        • 抢先式中断：系统首先把所有用户线程全部中断，如果发现有用户线程中断的地方不在安全点上，就恢复这条线程执行，让它一会再重新中断，直到跑到安全点上。
        • 主动式中断：当垃圾收集需要中断线程的时候，不直接对线程操作，仅仅简单地设置一个标志位，各个线程执行过程时会不停地主动去轮询这个标志，一旦发现中断标志为真时就自己在最近的安全点上主动中断挂起
          • 安全点就是指代码中包含这条轮询指令的位置。停在安全点后由JVM接管，利用预先生成好的OopMap，来解析和定位该线程执行上下文(栈和寄存器)中所有的对象引用，并将这些引用作为GC Roots的初始集合。
          • 要求高效，因此精简到一条汇编指令
    • 3.4.3 安全区域
      • 用户线程处于Sleep状态或者Blocked状态，这时候线程无法响应虚拟机的中断请求，不能再走到安全的地方去中断挂起自己，虚拟机也显然不可能持续等待线程重新被激活分配处理器时间。对于这种情况，就必须引入安全区域（Safe Region）来解决。
      • 安全区域是指能够确保在某一段代码片段之中，引用关系不会发生变化，因此，在这个区域中任意地方开始垃圾收集都是安全的。我们也可以把安全区域看作被扩展拉伸了的安全点。
    • 3.4.4 记忆集与卡表
      • 不止跨代引用需要记忆集，部分区域收集也需要
      • 记忆集是一种用于记录从非收集区域指向收集区域的指针集合的抽象数据结构
      • 如果不考虑空间占用和维护成本，可以记录全部的跨代引用对象
      • 但可以选择不同的记录粒度来节省记忆集的存储和维护成本
        • 1. 字长精度：每个记录精确到一个机器字长，该字包含跨代指针
        • 2. 对象精度：每个记录精确到一个对象，该对象包含跨代指针
        • 3. 卡精度：每个记录精确到一块内存区域，该区域包含跨代指针
          • 使用卡表实现。
          • 字节数组CARD_TABLE的每一个元素都对应着其标识的内存区域中一块特定大小的内存块，这个内存块被称作“卡页”（Card Page）。
          • 一个卡页的内存中通常包含不止一个对象，只要卡页内有一个（或更多）对象的字段存在着跨代指针，那就将对应卡表的数组元素的值标识为1，称为这个元素变脏（Dirty），没有则标识为0。在垃圾收集发生时，只要筛选出卡表中变脏的元素，就能轻易得出哪些卡页内存块中包含跨代指针，把它们加入GC Roots中一并扫描。
          • 卡表与卡页对应示意图
    • 3.4.5 写屏障
      • HotSpot虚拟机通过写屏障维护卡表状态
      • 写屏障可以看作在虚拟机层面对“引用类型字段赋值”这个动作的AOP切面，在引用对象赋值时会产生一个环形（Around）通知，供程序执行额外的动作，也就是说赋值的前后都在写屏障的覆盖范畴内
      • 为了避免伪共享，可以先检查卡表标记，只有当卡表元素未被标记过时才将其变脏
    • 3.4.6 并发的可达性分析
      • 并发标记：是为了解决 STW 停顿时间过长的问题
      • 三色标记：是分析并发标记的工具（白、灰、黑）
        • 白色 (White)：你还没检查过的房间（对象）。（可能是小偷/垃圾）
        • 灰色 (Gray)：你刚走进的房间（对象），你正在检查这个房间里的所有门（引用），看它们通向哪里。（工作队列）
        • 黑色 (Black)：你已经检查完的房间（对象），这个房间里的所有门（引用）你都看过了。（已确认是好人/存活）
      • 当且仅当以下两个条件同时满足时，会产生“对象消失”的问题，即原本应该是黑色的对象被误标为白色：
        • 赋值器插入了一条或多条从黑色对象到白色对象的新引用
          （开新门）：一个黑色对象（A）指向了一个白色对象（C）
        • 赋值器删除了全部从灰色对象到该白色对象的直接或间接引用
          （关旧门）：所有从灰色对象（B）到那个白色对象（C）的路径都被删除了
      • 解决方法：破坏两个条件之一
        • 增量更新 (Incremental Update) - (CMS 使用)
        • 原始快照 (SATB) - (G1, Shenandoah 使用)
  • 3.5 经典垃圾收集器
    • 如果两个收集器之间存在连线，就说明它们可以搭配使用
    • 3.5.1 Serial收集器
      • 它只会使用一个处理器或一条收集线程去完成垃圾收集工作，且在垃圾收集时必须暂停其他所有工作线程，直至收集完毕
      • Serial/Serial Old收集器运行示意图
      • 优点：没有线程交互的开销，有最高的单线程收集效率，且内存消耗最小，所以是客户端模式下的默认新生代收集器
    • 3.5.2 ParNew收集器
      • ParNew/Serial Old收集器运行示意图
      • 实质上是Serial收集器的多线程并行版本
      • 是不少运行在服务端模式下的HotSpot虚拟机，尤其是JDK 7之前的遗留系统中首选的新生代收集器，除了Serial收集器外，目前只有它能与CMS 收集器配合工作。
      • 自JDK 9开始，ParNew加CMS收集器的组合就不再是官方推荐的服务端模式下的收集器解决方案了，且ParNew和CMS从此只能互相搭配使用，再也没有其他收集器能够和它们配合了
      • 并行：描述的是多条垃圾收集器线程之间的关系，说明同一时间有多条这样的线程在协同工作，通常默认此时用户线程是处于等待状态。
      • 并发：描述的是垃圾收集器线程与用户线程之间的关系，说明同一间垃圾收集器线程与用户线程都在运行。由于用户线程并未被冻结，所以程序仍然能响应服务请求，但由于垃圾收集器线程占用了一部分系统资源，此时应用程序的处理的吞吐量将受到一定影响。
    • 3.5.3 Parallel Scavenge收集器
      • 也叫吞吐量优先收集器，是一款新生代收集器，同样是基于标记-复制算法实现的收集器，也是能够并行收集的多线程收集器
      • CMS等收集器的关注点是尽可能地缩短垃圾收集时用户线程的停顿时间，而Parallel Scavenge收集器的目标则是达到一个可控制的吞吐量
      • 吞吐量 = 运行用户代码时间 / （运行用户代码时间 + 垃圾收集时间）
      • 两个参数
        • 控制最大垃圾收集停顿时间的-XX：MaxGCPauseMillis参数，设置小会牺牲吞吐量和新生代空间，越小垃圾收集越频繁
        • 直接设置吞吐量大小的-XX：GCTimeRatio参数，也就是垃圾收集时间占总时间的比率，相当于吞吐量的倒数
    • 3.5.4 Serial Old收集器
      • Serial Old是Serial收集器的老年代版本，它同样是一个单线程收集器，使用标记-整理算法。
      • Serial/Serial Old收集器运行示意图
      • 主要供客户端模式下的HotSpot虚拟机使用，在服务端模式下，它也可能有两种用途：一种是在JDK 5以及之前的版本中与Parallel Scavenge收集器搭配使用，另外一种就是作为CMS收集器发生失败时的后备预案
    • 3.5.5 Parallel Old收集器
      • Parallel Old是Parallel Scavenge收集器的老年代版本，支持多线程并发收集，基于标记-整理算法实现。
      • Parallel Scavenge/Parallel Old收集器运行示意图
      • 在注重吞吐量或者处理器资源较为稀缺的场合，都可以优先考虑Parallel Scavenge加Parallel Old收集器这个组合
    • 3.5.6 CMS收集器
      • 是一种以获取最短回收停顿时间为目标的收集器
      • Concurrent Mark Sweep收集器运行示意图
      • 思想：四个阶段：
        • 初始标记：Stop-The-World，仅仅标记 GC Roots 本身 + GC Roots 直接引用的“下一层”对象，过程很快
        • 并发标记：用户线程恢复运行。垃圾回收线程从上一步标记的对象触发，遍历整个对象引用链，找出所有存活的对象并进行标记。这个过程和用户线程是并发的。
        • 重新标记（增量更新）：Stop-The-World，因为在”并发标记”阶段，用户线程还在运行，可能会改变某些对象的引用关系（比如一个对象本来要被回收，结果又被一个存活对象引用了）。这个阶段的任务就是修正这些变动，确保标记的最终准确性。这个阶段比初始标记稍长，但仍然很短。
        • 并发清除：用户线程恢复运行。垃圾回收线程开始清理所有未被标记的对象，回收它们占用的内存空间。这个过程也是和用户线程并发执行的。
      • 优点：耗时最长的并发标记和并发清除阶段和用户线程一起工作，是HotSpot追求低停顿第一次成功尝试
      • 缺点：
        • 对处理器资源敏感，并发设计会占用一部分线程导致应用程序变慢
        • 无法处理在标记过程中产生的“浮动垃圾”，需要留到下一次处理，但因为是并发的所以要预留内存给用户线程，如果内存空间不够会导致并发失败从而触发STW的Full GC
        • 会产生大量空间碎片，因为CMS基于“标记-清除”算法，会导致Ful GC
    • 3.5.7 Garbage First收集器
      • 开创了收集器面向局部收集的设计思路和基于Region的内存布局形式
        • JDK 9发布之日，G1取代Parallel Scavenge加Parallel Old组合，成为服务端模式下的默认垃圾收集器，而CMS则沦落至被声明为不推荐使用（Deprecate）的收集器
        • G1不再坚持固定大小以及固定数量的分代区域划分，而是把连续的Java堆划分为多个大小相等的独立区域（Region），每一个Region都可以根据需要，扮演新生代的Eden空间、Survivor空间，或者老年代空间。Region中还有一类特殊的Humongous区域，专门用来存储大对象。G1认为只要大小超过了一个 Region容量一半的对象即可判定为大对象。
        • Mixed GC：面向堆内存任何部分组成回收集进行回收，衡量标准不再是它属于哪个分代，而且哪块区域存放的垃圾数量最多，回收效益最大
        • 建立时间停顿模型：可以支持指定在长度为M毫秒的时间片段内，消耗在垃圾收集上的时间大概率不超过N毫秒的目标
        • G1收集器Region分区示意图
        • G1收集器跟踪各个Region里面的垃圾堆积的“价值”大小，然后在后台维护一个优先级列表，每次根据用户设定允许的收集停顿时间，优先处理回收价值收益最大的那些Region，这也就是“Garbage First”名字的由来。每次收集到的内存空间都是Region大小的整数倍
          价值即回收所获得的空间大小以及回收所需时间的经验值
        • 关键问题：
          • 怎么需要处理跨Region引用：每个Region维护自己的记忆集（哈希表），这些记忆集会记录别的Region指向自己的指针，并标记这些指针分别在哪些卡页范围之内，因此G1至少要耗费大约相当于Java堆容量10%至20%的额外内存来维持收集器工作
          • 并发阶段如何保证线程与用户线程互不干扰的运行：原始快照。此外，G1为每一个Region设计了两个TAMS的指针，把Region中的一部分空间划分出来用于并发回收过程中新对象的分配，这新对象地址必须在这两个指针范围上，且这新对象默认是存活的不回收。如果内存回收速度赶不上内存分配，也会产生STW的Full GC。
          • 怎么建立可靠的停顿预测模型：以衰减均值为理论基础来实现的，在垃圾收集过程中，G1收集器会记录每个Region的回收耗时、每个Region记忆集里的脏卡数量等各个可测量的步骤花费的成本，并分析得出平均值、标准偏差、置信度等统计信息，衰减平均值更准确地代表“最近的”平均状态
        • 运行思想：跟CMS类似，也分为四个阶段。并非纯粹地追求低延迟，目标是在延迟可控的情况下获得尽可能高的吞吐量
        • 初始标记：短暂Stop-The-World，只标记GC Roots能直接关联到的对象，并且修改TAMS指针的值使下一阶段并发标记用户线程还能分配新对象
        • 并发标记：进行GC Roots Tracing的过程
        • 最终标记：短暂Stop-The-World，修正并发标记期间，因程序运行导致标记发生变化的那一部分对象
        • 筛选回收：Stop-The-World，多条收集器线程并行完成。根据时间来进行价值最大化的回收更新Region的统计数据，对各个Region的回收价值和成本进行排序，根据用户所期望的停顿时间来制定回收计划，可以自由选择任意多个Region构成回收集，然后把决定回收的那一部分Region的存活对象复制到空的Region中，再清理掉整个旧Region的全部空间
          优势： 1.没有内存碎片：因为是把存活对象整体复制到新区域，所以内存总是紧凑的，从根本上解决了CMS的碎片问题。这是一种标记-整理思想的体现。G1从整体来看是基于“标记-整理”算法实现的收集器，但从局部（两个Region之间）上看又是基于“标记-复制”算法实现。 2.停顿可预测：我可以告诉G1,“这次GC的停顿时间不要超过200毫秒”。G1就会根据这个目标，只选择在200毫秒内能回收完的、最有价值的那几个Region进行回收，而不是每次都回收所有垃圾。 3.“Garbage-First”名字的由来：G1的名字就来源于它的核心思想——优先回收垃圾最多(价值最大)的区域，从而保证在有限的停顿时间内，垃圾回收的效率最高。
      • 相比CMS：G1无论是为了垃圾收集产生的内存占用还是程序运行时的额外执行负载都要更高
  • 3.6 低延迟垃圾收集器
    • 不可能三角：内存占用、吞吐量、延迟，但延迟的重要性越来越大
    • 3.6.1 Shenandoah收集器
      • 目标是实现一种能在任何堆内存大小下都可以把垃圾收集的停顿时间限制在十毫秒以内的垃圾收集器
      • 工作过程：
      • 与G1至少有三个不同之处
        • 支持并发的整理算法：Brooks提出的新方案不需要用到内存保护陷阱，而是在原有对象布局结构的最前面统一增加一个新的引用字段，在正常不处于并发移动的情况下，该引用指向对象自己
        • 默认不使用分代收集，不会有专门的新生代Region或老年代Region
        • 放弃了G1的记忆集，改用连接矩阵来记录跨Region的引用关系，降低了维护消耗和伪共享的发生概率
          如果Region N有对象指向Region M，就在表格的N行M列中打上一个标记，如图所示，如果Region 5中的对象Baz引用了Region 3的Foo，Foo又引用了Region 1的Bar，那连接矩阵中的5行3列、3行1列就应该被打上标记。在回收时通过这张表格就可以得出哪些Region之间产生了跨代引用。
    • 3.6.2 ZGC收集器
      • 目标与Shenandoah收集器目标高度相似，但是实现思路两者有显著差异
      • ZGC收集器是一款基于Region内存布局的，（暂时）不设分代的，使用了读屏障、染色指针和内存多重映射等技术来实现可并发的标记-整理算法的，以低延迟为首要目标的一款垃圾收集器。
        • 基于Region的堆内存布局：
          • 小型Region：容量固定为2MB，用于放置小于256KB的小对象
          • 中型Region：容量固定为32MB，用于放置大于等于256KB但小于4MB的对象
          • 大型Region：容量不固定，可以动态变化，但必须为2MB的整数倍，用于放置4MB或以上的大对象。每个大型Region中只会存放一个大对象
        • 染色指针：是一种直接将少量额外的信息存储在指针上的技术，直接把标记信息记在引用对象的指针上
          HotSpot虚拟机的几种收集器有不同的标记实现方案，有的把标记直接记录在对象头上（如Serial收集器），有的把标记记录在与对象相互独立的数据结构上（如G1、Shenandoah使用了一种相当于堆内存的1/64大小的，称为BitMap的结构来记录标记信息），而ZGC的染色指针是最直接的、最纯粹的，它直接把标记信息记在引用对象的指针上，这时，与其说可达性分析是遍历对象图来标记对象，还不如说是遍历“引用图”来标记“引用”了。
  • 3.7 选择合适的垃圾收集器
    • 3.7.1 Epsilon收集器
      • 无操作的收集器。如果应用只要运行数分钟甚至数秒， 只要Java虚拟机能正确分配内存，在堆耗尽之前就会退出，那显然运行负载极小、没有任何回收行为的Epsilon便是很恰当的选择
        而事实上只要Java虚拟机能够工作，垃圾收集器便不可能是真正“无操作”的。原因是“垃圾收集器”这个名字并不能形容它全部的职责，更贴切的名字应该是本书为这一部分所取的标题——“自动内存管理子系统”。一个垃圾收集器除了垃圾收集这个本职工作之外，它还要负责堆的管理与布局、对象的分配、与解释器的协作、与编译器的协作、与监控子系统协作等职责，其中至少堆的管理和对象的分配这部分功能是Java虚拟机能够正常运作的必要支持，是一个最小化功能的垃圾收集器也必须实现的内容。从JDK 10开始，为了隔离垃圾收集器与Java虚拟机解释、编译、监控等子系统的关系，RedHat提出了垃圾收集器的统一接口，即JEP 304提案，Epsilon是这个接口的有效性验证和参考实现，同时也用于需要剥离垃圾收集器影响的性能测试和压力测试。
    • 3.7.2 收集器的权衡
      • 三个因素影响：
        • 应用程序的主要关注点：如果是数据分析、科学计算类的任务，目标是能尽快算出结果，那吞吐量就是主要关注点；如果是SLA应用，那停顿时间直接影响服务质量，严重的甚至会导致事务超时，这样延迟就是主要关注点；而如果是客户端应用或者嵌入式应用，那垃圾收集的内存占用则是不可忽视的。
        • 运行应用的基础设施：譬如硬件规格，要涉及的系统架构是x86-32/64、SPARC还是ARM/Aarch64；处理器的数量多少，分配内存的大小；选择的操作系统是Linux、Solaris还是Windows等
        • 使用JDK的发行商、版本号：是ZingJDK/Zulu、OracleJDK、Open-JDK、OpenJ9抑或是其他公司的发行版？该JDK对应了《Java虚拟机规范》的哪个版本？
    • 3.7.3 虚拟机及垃圾收集器日志
      • JDK 9开始，HotSpot所有功能的日志都收归到了“-Xlog”参数上
      • 命令行：-Xlog[:[selector][:[output][:[decorators][:output-options]]]]
        • 最关键的参数是选择器（Selector），它由标签（Tag）和日志级别（Level）共同组成
          • 标签可理解为虚拟机中某个功能模块的名字，它告诉日志框架用户希望得到虚拟机哪些功能的日志输出。垃圾收集器的标签名称为“gc”
          • 日志级别从低到高，共有Trace，Debug，Info，Warning，Error，Off六种级别，日志级别决定了输出信息的详细程度
        • 还可以使用修饰器（Decorator）来要求每行日志输出都附加上额外的内容，支持附加在日志行上的信息包括：
          • time：当前日期和时间。
          • uptime：虚拟机启动到现在经过的时间，以秒为单位。
          • timemillis：当前时间的毫秒数，相当于System.currentTimeMillis()的输出。
          • uptimemillis：虚拟机启动到现在经过的毫秒数。
          • timenanos：当前时间的纳秒数，相当于System.nanoTime()的输出。
          • uptimenanos：虚拟机启动到现在经过的纳秒数。
          • pid：进程ID。
          • tid：线程ID。
          • level：日志级别。·tags：日志输出的标签集。
          • 如果不指定，默认值是uptime、level、tags这三个
            此时日志输出类似于以下形式：[3.080s][info][gc,cpu] GC(5) User=0.03s Sys=0.00s Real=0.01s
  • 3.8 实战：内存分配与回收策略
    • 3.8.1 对象优先在Eden分配
      • 大多数情况下，对象在新生代Eden区中分配。当Eden区没有足够空间进行分配时，虚拟机将发起 一次Minor GC
    • 3.8.2 大对象直接进入老年代
      • 大对象就是指需要大量连续内存空间的Java对象，最典型的大对象便是那种很长的字符串，或者元素数量很庞大的数组
        在分配空间时，它容易导致内存明明还有不少空间时就提前触发垃圾收集，以获取足够的连续空间才能安置好它们，而当复制对象时，大对象就意味着高额的内存复制开销
      • -XX：PretenureSizeThreshold参数指定大于该设置值的对象直接在老年代分配
    • 3.8.3 长期存活的对象将进入老年代
      • 虚拟机给每个对象定义了一个对象年龄（Age）计数器，存储在对象头中（详见第2章）。对象通常在Eden区里诞生，如果经过第一次 Minor GC后仍然存活，并且能被Survivor容纳的话，该对象会被移动到Survivor空间中，并且将其对象年龄设为1岁。对象在Survivor区中每熬过一次Minor GC，年龄就增加1岁，当它的年龄增加到一定程 度（默认为15），就会被晋升到老年代中
      • 参数-XX：MaxTenuringThreshold可以设置对象晋升老年代的年龄阈值
    • 3.8.4 动态对象年龄判定
      • HotSpot虚拟机并不是永远要求对象的年龄必须达到- XX：MaxTenuringThreshold才能晋升老年代，如果在Survivor空间中相同年龄所有对象大小的总和大于 Survivor空间的一半，年龄大于或等于该年龄的对象就可以直接进入老年代，无须等到-XX： MaxTenuringThreshold中要求的年龄
    • 3.8.5 空间分配担保
      • 在发生Minor GC之前，虚拟机必须先检查老年代最大可用的连续空间是否大于新生代所有对象总空间，如果这个条件成立，那这一次Minor GC可以确保是安全的。如果不成立，则虚拟机会先查看- XX：HandlePromotionFailure参数的设置值是否允许担保失败；如果允许，那会继续检查老年代最大可用的连续空间是否大于历次晋升到老年代对象的平均大小，如果大于，将尝试进行一次Minor GC，尽管这次Minor GC是有风险的；如果小于，或者不允许冒险，那这时就要改为进行一次Full GC。
        • 最极端的情况就是内存回收后新生代中所有对象都存活，需要老年代进行分配担保，把Survivor无法容纳的对象直接送入老年代
        • JDK 6 Update 24之后的规则变为只要老年代的连续空间大于新生代对象总大小或者历次晋升的平均大小，就会进行Minor GC，否则将进行Full GC
